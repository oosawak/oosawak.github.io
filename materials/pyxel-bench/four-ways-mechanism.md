# Pyxel のゲームを4方式で動かす ― 仕組みの比較

同じゲーム「CubeBoy」（と「LINE BOY」）を、4つの方式でブラウザ向けに実装して並べた比較の、仕組み編です。
ゲームの出来ではなく、「どの土台に乗せて、どう運んで、ブラウザでどう実行するか」の違いを整理します。
実測の数字は材料として小さく添えています（数値の正本は同じフォルダの RESULTS.md、2026年11月6日計測）。
コードそのものの見比べは [four-ways-code.md](four-ways-code.md) を参照してください。

## 要点

4方式の違いは、**土台（エンジン）の出自**と**運び方**の組み合わせです。

- **本家 Pyxel**: 土台は公式エンジン（Python）。Python の実行環境ごと運び、ブラウザの中で解釈しながら実行する。
- **pyxel-rust**: 土台は互換エンジン（Rust で実装し直し）。エンジンとゲームを WASM に固めて運び、ブラウザが直接実行する。
- **素の JavaScript**: 土台になるエンジンは無い。ブラウザ標準の機能（Canvas 2D）の上に、ゲームを素の JavaScript で書く。入力・音・ループなどの共通部品だけ、HTML プレイヤーの共通ライブラリ（hp.js）が担う。
- **rustgames**: 土台は自前基盤（Rust＋wgpu）。自作エンジンと全タイトルを単一の WASM に固めて運び、描画は GPU（wgpu）経由。

## 方式1: 本家 Pyxel（Python）

- エンジン本体が Python 製のレトロゲームエンジンです（利用者から見えるエンジンとゲームは Python）。
- ゲームは Python のコードとして書かれ、実行時に解釈されて動きます。
- ブラウザ版で読み込む中身は「Python 実行環境（Pyodide 一式）＋ Pyxel エンジン ＋ ゲームのコード」。まず実行環境を読み込み・立ち上げてから、ゲームが動き出します。
- フレームの回し方は、利用者が書いた update（更新）と draw（描画）の関数を、エンジンの run が繰り返し呼ぶ形です。
- 描画や音は、Pyodide 上のエンジンが担います。

## 方式2: pyxel-rust（Rust／WASM、Pyxel 互換）

- Pyxel そのものを移植したのではなく、エンジンを Rust で実装し直したライブラリです（Pyxel にインスパイアされたもの、とリポジトリにあります）。
- Pyxel 互換の API（`init`、`run`、`cls`、`blt`、`text` など主要なもの）を Rust 側で実装していて、ゲームも Rust で書きます。update／draw を run が回す、というフレームの型は本家に合わせています。
- ブラウザ向けには、エンジンとゲームをまとめて WASM にコンパイルします（`wasm-bindgen`／`wasm-pack`、ターゲットは `wasm32-unknown-unknown`）。配布物は「WASM モジュール（エンジン＋ゲーム）」で、Python 実行環境は含まれません。
- ブラウザでの描画は `web-sys` 経由の Canvas 2D です。デスクトップでは SDL2／wgpu のバックエンドもあります。開発中のプロジェクトで、仕様は変わる可能性があります。

互換の範囲の要点（詳しくは [pyxel-vs-pyxel-rust.md](pyxel-vs-pyxel-rust.md) の「互換の範囲」の節）: 公開ページに対応表があり、Pyxel 3.0.0 の公式 API 全741項目について、ブラウザ／WASM では「実装あり 591・一部対応 46・未対応 104」です。「実装あり」は「Rust から使える相当機能がある」という意味で、公式 Python API との完全互換を意味しない、と明記されています。

## 方式3: 素の JavaScript

- エンジンは使いません。ゲームは1枚の HTML ファイルに収まり、描画は Canvas 2D の API（`fillRect`、`arc` など）を直接呼んで行います。
- 土台として使うのは、HTML プレイヤーの共通ライブラリ hp.js です。担うのは「エンジン」ではなくプレイヤー側の共通部品で、入力（キーボードとゲームパッドをまとめて `HP.left()`／`HP.a()` のように返す）、効果音（`HP.beep()`）、シーン管理（`HP.scene()`）、ループの駆動（`HP.loop()`、requestAnimationFrame から経過時間を渡す）を受け持ちます。共有部品はプレイヤー側が持つ、という HTML プレイヤーの設計どおりの分担です。
- Pyxel の作法（update／draw の型、色、タイルマップ）は API として用意されるのではなく、ゲーム側が自分で書き方を似せて用意しています。色も Pyxel の色番号ではなく、`"#2B335F"` のような色の値を直接持ちます。
- フレームの回し方も自前です。HP.loop から受け取る経過時間を蓄積し、30Hz の固定ステップで `step()` を回す形を、ゲーム側のコードで書いています。
- コンパイルも実行環境の読み込みも無いので、配布物は HTML＋JavaScript だけで、転送量は4方式で最小です。

## 方式4: rustgames（Rust＋wgpu、自前基盤）

- 本人の自前ゲーム基盤です。エンジン部分（`engine` や、wasm 向けの描画層など）もゲームも Rust で書かれています。
- ブラウザ向けは、エンジンと**全タイトル**をまとめた単一の WASM モジュール（`wasm_app`）として配ります。CubeBoy 用のページも LINE BOY 用のページも、読み込んでいる wasm は同一バイナリ（約3.55MB）です。
- 描画は Canvas 2D ではなく、wgpu 経由の GPU 描画です。2D ゲーム向けには自作の 2D バッチ層（render2d）があり、仮想解像度（CubeBoy では 128×128）をキャンバスへレターボックス拡大し、矩形・線・三角形・円を色付き頂点で1ドローコールにバッチ化します。テクスチャは使わず、文字も 5×7 ビットマップフォントを頂点で描きます。
- フレームの回し方はゲーム側の `tick(時刻)` が担います。ページ側の JavaScript が requestAnimationFrame から `tick_cubeboy(ts)` を呼び、30Hz 固定ステップの蓄積・消化（最大4ステップ）→ 描画 → レンダラーへ提出、までを1回にまとめています。入力はページ側がキーボード状態をビットマスクにして `set_input_cubeboy(mask)` で渡します。
- 起動時は wasm のコンパイルが入るぶん、pyxel-rust より動き出しが遅めです。

## 仕組みの比較表

| 観点 | 本家 Pyxel | pyxel-rust | 素の JavaScript | rustgames |
|---|---|---|---|---|
| 言語 | Python | Rust | JavaScript | Rust |
| 土台（エンジン）の出自 | 公式（Pyxel 本体） | 互換（Rust で実装し直し） | 無し（ブラウザ標準＋プレイヤー共通部品 hp.js） | 自前（自作基盤） |
| ブラウザでの実行方式 | Pyodide の上で Python コードを解釈実行 | WASM モジュールをブラウザが直接実行 | ブラウザが JavaScript をそのまま実行 | WASM モジュールをブラウザが直接実行 |
| 配布物の内訳 | Python 実行環境 ＋ エンジン ＋ ゲームコード | WASM モジュール（エンジン＋そのゲーム） | HTML ＋ JavaScript（ゲームのみ） | 単一 WASM（エンジン＋全タイトル）＋ ページの HTML／JS |
| 描画の経路 | Pyodide 上のエンジンが描画 | Canvas 2D（web-sys 経由） | Canvas 2D（直接） | wgpu（自作 2D バッチ層 render2d） |
| フレームの回し方 | update／draw を run が呼ぶ | 同じ型（互換 API として踏襲） | 自前（30Hz 固定ステップを自力で実装） | 自前（tick が固定ステップ＋描画を担当） |
| 動き出し方 | 実行環境を読み込み・立ち上げてから | コンパイル済みモジュールを読み込めば開始 | 読み込めば即時 | wasm のコンパイル分だけ余計にかかる |

## 仕組みの差が、数字に出ると

実測（ヘッドレス Chrome・ローカル配信、各2回の平均寄り）は次のとおりです。

### CubeBoy

| 方式 | 転送量 | 動き出すまで | FPS（計測器内） | スクリプトCPU |
|---|---|---|---|---|
| 本家 Pyxel | 約27.4MB | 約5.4秒 | 61.5（上限） | 約0.2% |
| pyxel-rust | 約2.1MB | 約1.0秒 | 61.5（上限） | 約1.5% |
| 素の JavaScript | 約0.14MB | 約2.2秒 | ※1 | 約0.6% |
| rustgames | 約3.65MB ※2 | 約3.0秒 | 7.4 ※1 | 約2.6% |

### LINE BOY

| 方式 | 転送量 | 動き出すまで | FPS（計測器内） | スクリプトCPU |
|---|---|---|---|---|
| 本家 Pyxel | 約29.3MB | 約1.5秒 | 60.4 | 約0.2% |
| pyxel-rust | 約2.0MB | 約0.9秒 | 58.5 | 約3.3% |
| 素の JavaScript | 約0.15MB | 約1.4秒 | ※1 | 約1.3% |
| rustgames | 約3.65MB ※2 | 約2.2秒 | 11.2 ※1 | 約2.3% |

読み方の注意:

- ※1 FPS の注意: JavaScript 版と rustgames 版の「提示フレーム数」は、このヘッドレス環境（SwiftShader のソフトウェア描画）で低く出ました。JavaScript 版は、フレーム生成を促す条件では requestAnimationFrame が約62/秒で回ることを別途確認しています。rustgames 版も、既存の wgpu タイトルが同じ環境で低く出る傾向がありました。どちらも実機ブラウザでの体感速度ではなく、計測器の癖として読んでください。Pyxel と pyxel-rust は計測器内でも表示上限（約60）に張り付きました。
- ※2 rustgames の転送量は、エンジン＋全タイトルを含む単一 wasm（約3.55MB）にページの HTML／JS を加えた値です。ゲーム単体の増分ではないので、他の方式の「そのゲームだけの重さ」とは性質が違います。
- 本家 Pyxel の転送量が桁違いなのは、Pyxel 本体（wheel 約4.7MB）に加えて Pyodide 一式を毎回読み込むためです。「実行環境ごと運ぶ」ことの代金が、そのまま数字に出ています。
- これらの数字は「方式そのものの実力差」ではなく「この実装の実測」です。同じゲームでも、コードは方式ごとに別物です（出自の系統は [four-ways-code.md](four-ways-code.md) を参照）。

## 向いている使い方の整理

- **本家 Pyxel**: Python のまま書けて、Pyxel のエディタ・作例・公開ゲームの資産がそのまま使えるのが強みです。配布時は、初回読み込みの重さを受け止める場面かどうかが分かれ目になります。
- **pyxel-rust**: 実行環境を持たないぶん読み込みが軽く、Web 配布の立ち上がりが速い形です。代わりにゲームは Rust で書き直すことになり、開発中ゆえの仕様変更も引き受けます。
- **素の JavaScript**: 配るものが一番軽く、ブラウザさえあれば追加の土台なしで動きます。代わりに、エンジンが用意してくれる作法（フレームの回し方、描画・入力の API）は全部自分で用意します。プレイヤーの共通部品（hp.js）のような受け皿があると、その分担が効きます。
- **rustgames**: 全タイトルを1つの基盤に載せるので、タイトルが増えるほど1本あたりの追加は小さくなります。GPU 描画の土台も含めて自前で持つぶん、最初の1本は重くなります。3D など GPU が効くタイトルと土台を共有できるのが、この形の狙いです。

「公式の土台に乗るか、互換の土台を作るか、自前の基盤を持つか、土台なしで書くか」。4方式は、言語の違いというより、土台の選び方と運び方の違いとして並んでいます。
