# Pyxel と pyxel-rust ― 仕組みの違い

> 4方式版を作りました。素の JavaScript と rustgames を加えた仕組みの比較は [four-ways-mechanism.md](four-ways-mechanism.md)、コードの見比べは [four-ways-code.md](four-ways-code.md) を参照してください。

同じ「Pyxel のゲーム」でも、ブラウザの中で動いている仕組みは別物です。
この資料は、ゲームの出来ではなく、エンジンの仕組みの違いを整理したものです。
実測の数字は、仕組みの差がどう表れるかを見る材料として、最後に小さく添えています（数値の正本は同じフォルダの RESULTS.md、2026年11月6日計測）。

## 要点

違いの芯は、ブラウザへ「何を運ぶか」です。

- **本家 Pyxel** は、Python の実行環境ごと運びます。ブラウザの中で Python 環境（Pyodide）を立ち上げ、その上でエンジンとゲームの Python コードを解釈しながら実行します。
- **pyxel-rust** は、エンジンとゲームを機械語（WebAssembly）に固めて運びます。ブラウザは WASM を直接実行するので、Python の実行環境は入りません。

## 本家 Pyxel の仕組み

- エンジン本体が Python 製のレトロゲームエンジンです（中核の一部は別言語でも、利用者から見えるエンジンとゲームは Python）。
- ゲームは Python のコードとして書かれ、実行時に解釈されて動きます。
- ブラウザ版では、読み込む中身は「Python 実行環境（Pyodide 一式）＋ Pyxel エンジン ＋ ゲームのコード」です。まず実行環境を読み込み、立ち上げてから、ゲームが動き出します。
- フレームの回し方は、利用者が書いた update（更新）と draw（描画）の関数を、エンジンの run が繰り返し呼ぶ形です。

## pyxel-rust の仕組み

- Pyxel そのものを移植したのではなく、エンジンを Rust で実装し直したライブラリです（Pyxel にインスパイアされたもの、とリポジトリにあります）。
- Pyxel 互換の API（`init`、`run`、`cls`、`blt`、`text` など主要なもの）を Rust 側で実装していて、ゲームも Rust で書きます。update／draw を run が回す、というフレームの型は本家に合わせています。
- ブラウザ向けには、エンジンとゲームをまとめて WASM にコンパイルします（`wasm-bindgen`／`wasm-pack`、ターゲットは `wasm32-unknown-unknown`）。配布物は「WASM モジュール（エンジン＋ゲーム）」で、Python 実行環境は含まれません。
- 描画・音・入力はバックエンドで分かれています。ブラウザでは `web-sys` 経由で Canvas 2D API を使って描きます。デスクトップでは pyxel-core（SDL2）または wgpu のバックエンドで動きます。API は graphics、input、audio、system、math などのモジュールに分かれた構成です。
- 開発中のプロジェクトで、API や仕様は予告なく変わる可能性があると明記されています。

## 仕組みの比較表

| 観点 | 本家 Pyxel | pyxel-rust |
|---|---|---|
| エンジンの言語 | Python | Rust（実装し直し） |
| ゲームの書き方 | Python のコード | Rust のコード（互換 API を呼ぶ） |
| ブラウザでの実行方式 | Pyodide の上で Python コードを解釈実行 | WASM モジュールをブラウザが直接実行 |
| 配布物の内訳 | Python 実行環境 ＋ エンジン ＋ ゲームコード | WASM モジュール（エンジン＋ゲーム） |
| 動き出し方 | 実行環境を読み込み・立ち上げてから実行 | コンパイル済みモジュールを読み込めば実行開始 |
| フレームの回し方 | update／draw を run が呼ぶ | 同じ型（互換 API として踏襲） |
| ブラウザでの描画 | Pyodide 上のエンジンが描画 | web-sys 経由で Canvas 2D |
| ブラウザ以外の実行 | ―（本資料では Web 版を対象） | デスクトップバックエンド（SDL2／wgpu）あり |

## 仕組みの差が、数字に出ると

実測（CubeBoy、ヘッドレス Chrome・ローカル配信）では、転送量が本家 約27.4MB に対して pyxel-rust 約2.1MB、動き出すまでは約5.4秒に対して約1.0秒でした。
これは速さ比べというより、「実行環境ごと運ぶ」ことの代金が、そのまま読み込みの重さとして出たものと読めます。本家は Pyxel 本体（wheel 約4.7MB）に加えて Pyodide 一式を毎回読み込むため、転送量が桁違いになります。
逆に実行中の CPU は pyxel-rust のほうが多めでした（同じ計測の LINE BOY で、本家 約0.2% に対して約3.3%。それでも軽い範囲です）。

数字の読み方には注意が要ります。

- これらは「方式そのものの実力差」ではなく「この実装の実測」です。同じゲームでも、コードは方式ごとに別物です。
- FPS にはヘッドレス計測の癖があり、実機ブラウザでの体感速度とは分けて読んでください（詳しくは RESULTS.md）。

## 向いている使い方の整理

- **本家 Pyxel**： Python のまま書けて、Pyxel のエディタ・作例・公開ゲームの資産がそのまま使えるのが強みです。配布時は、初回読み込みの重さを受け止める場面かどうかが分かれ目になります。
- **pyxel-rust**： 実行環境を持たないぶん読み込みが軽く、Web 配布の立ち上がりが速い形です。代わりにゲームは Rust で書き直すことになり、開発中ゆえの仕様変更も引き受けます。

「Python のまま動かすか、Rust で WASM に固めるか」。選んでいるのは言語というより、運び方の仕組みのほうだと思います。

## 互換の範囲（公開ページの対応表から）

pyxel-rust の公開ページには、Pyxel 3.0.0 の公式 API リファレンスを基準にした対応表があります（全741項目・26分類）。冒頭で「全機能対応ではありません」と明記され、「実装あり」は「Rust から使える相当機能がある」ことを示すだけで、公式 Python API との完全互換を意味しない、とされています。空処理や固定値を返すだけのものは「未対応」に数える、という基準です。

バックエンド別の集計は次のとおりです。

| バックエンド | 実装あり | 一部対応 | 未対応 |
|---|---|---|---|
| ブラウザ／WASM | 591 | 46 | 104 |
| デスクトップ／SDL2 | 652 | 37 | 52 |
| デスクトップ／wgpu | 384 | 14 | 343 |

同じ741項目でも、バックエンドで対応状況が大きく違います。ブラウザ／WASM で未対応の代表は、screenshot や screencast、load／save まわり、text などです。一部対応のものは、init のように引数が絞られている（width／height／title／fps のみ）など、制限の内容が項目ごとに書かれています。

対応表: [Pyxel 全機能の対応状況](https://oosawak.github.io/pyxel-rust/examples/retro3d/#compatibility)
