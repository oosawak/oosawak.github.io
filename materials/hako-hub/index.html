hako（箱）のカタログ

Hako Hub

箱の中身のカタログです。Docker Hub のように巨大なイメージを置くのではなく、数KBのレシピ（設定ファイル）を置きます。 VS Code や Forgejo のようなソフトは箱に同梱せず、ここからレシピを取って、その場で入れる形です。 人がブラウザで読むカタログと、hako コマンドが読む定義は、同じものを使います。

hako は独立した土台です。土台とレシピの仕組みだけを用意しておき、その上に用途ごとの構成を載せます。ソース管理の道具一式を載せた構成は、その一例です。 アプリ本体は約12 MiB と小さく、SSH サーバーまで含めて最初から入っているのは入り口と土台だけです。

土台を選ぶ

土台は、この枠で選びます。選ぶと、下のカタログがその土台に合わせて見えます。使えない物は消えずに、薄くなって「この土台では使えません」と出ます。

土台の詳細： Ubuntu 24.04 ／ Alpine 3.24 ／ Bionicのみ（土台なし） ｜ 将来の候補： Ubuntu 26.04 ／ Fedora ／ Arch Linux ／ Debian

初回セットアップでは、土台と一緒に、初期ユーザー名（既定は hako）と、そのパスワード、root のパスワード（空欄なら初期ユーザーと共通）を設定します。パスワードが未設定の間は、SSH は開きません。パスワードは6文字から受け付け、8文字以上を推奨します（初期ユーザー・root・SSH のパスワード共通です）。

使い方

  • hako list ― 使えるレシピと、導入の状態の一覧
  • hako up 名前 ― 未導入ならレシピに沿って自動で入れて、起動する
  • hako ps ― 稼働中のサービスの一覧
  • hako down 名前 ― 停止する（データは残る）
  • hako remove 名前 ― 作業場所ごと片付ける

安全のための線引き

箱の中では、個別のパッケージを足す操作（apt install）は自由です。一方、土台をまとめて新しくする操作（apt upgrade）は、案内を出して止める仕組みが入っています。 proot の変換の仕組みと新しいライブラリが合わず、箱が動かなくなるのを防ぐためです。土台を上げる時は、新しい土台（rootfs）に差し替える形で行います。

GitHub から入れる仕組み

このカタログの正本は GitHub にあります。箱の中の hako は、GitHub からレシピ（設定ファイル）を取ってきて、その通りにソフトを入れます。

GitHub で公開されている OSS は、リリースに実行ファイルが出ていれば、レシピでそのまま入れられます。Forgejo や code-server が、その形です（本体は GitHub のリリースから取り、ハッシュで照合します）。ソースしか無い物は、箱の中で組み立てる形になります。電話（arm64）では、arm64 向けの実行ファイルが出ているかどうかが分かれ目です。

機械が読む一覧は catalog.json にあります（全項目の名前・状態・版・コマンド）。

更新があるかどうかは、箱が入手先（GitHub のリリースや、パッケージの置き場）を見に行って、今入っている版と比べて知ります。勝手に上げることはせず、「新しい版あり」を知らせて、上げるかどうかは hako up で決める形です。

土台と標準ライブラリ

「この土台で使えるか」は、物の種類で決まります。土台のパッケージで入れる物は、パッケージ置き場がその土台で動く物だけを置いているので、どの土台でも入ります。前提の標準ライブラリが効くのは、公式の実行ファイルを取る物だけです。ネイティブ部品は、Bionic の世界で動きます。

  • glibc ― Ubuntu、Debian、Fedora、Arch の土台。配布されている実行ファイルは、この前提で作られている物が多い
  • musl ― Alpine の土台。軽いのが特徴。glibc 前提の実行ファイルは、そのままでは動かない
  • Bionic ― Android の標準ライブラリ。箱のネイティブ側の部品（制御コア、git、sshd など）は、この前提で作られている

公式の実行ファイルが Alpine で動かないのは、glibc 前提で作られていて、Alpine 側は musl だからです。逆に、Bionic 向けに作った部品は、土台が無くても動きます。
