## 概要

Hako@Linux は、Android の電話の中に Linux の箱を作る仕組みです。\
仮想マシンは使いません。\
電話のカーネルをそのまま使って、土台と部品を組み合わせます。\

![Hako@Linux のアプリアイコン。ガラスの箱に閉じ込められたペンギン](tech/hako-at-linux-icon-v1.jpg)
アプリ本体（APK）は 15.80 MiB です。\
SSH サーバーまで含めてこの小ささなのは、サービスを同梱せず、後から足す作りにしたためです。\
これは開発中の仕組みで、この記事はその技術資料です。\
販売予定の全部入りの製品（PocketGit）とは、別のラインで作っています。

![Hako@Linux の状態画面。Alpine 3.24 が稼働中で、接続情報と土台切り替えの記録が出ている](tech/hako-at-linux-status-v1.jpg)

## 設計方針

方針は3つです。\
1つ目は、同梱しないことです。\
Hako@Linux が最初から持つのは、入り口と制御と土台だけです。\
Forgejo や code-server のようなサービスは、レシピ（設定ファイル）で後から足します。\
2つ目は、電話の画面は状態確認とボタンだけにすることです。\
操作は、PC から SSH で入って行います。\
Android からは、Termius などの SSH アプリで入ってください。\
3つ目は、自作して足す機能は、まず Bionic（Android の標準ライブラリ）側で必ず動く形にすることです。\
土台に依存しない部品が増えるほど、箱は壊れにくくなります。

## 構成

作りは、大きく3つの層に分かれています。

### 1 ネイティブ側の部品

Android のプロセスとして直接動く部品です。\
中心は、Rust で書いた制御コア（約400KB）です。\
サービスの起動と停止、設定の生成、状態の確認を担います。\
git と基本コマンド（uutils の coreutils）と bash も、ネイティブで入っています。\
jq と SQLite と tmux と Vim も、ネイティブの部品として足しました。\
一番大きいのは Vim で、無いと私が困るので入っています。\
SSH サーバーも、後で述べる理由でネイティブ側に置きました。

### 2 proot と土台

土台（Ubuntu や Alpine のファイル一式）は、proot の中で動きます。\
proot は、プログラムのシステムコールを ptrace で受け止めて変換する仕組みです。\
root 権限がなくても、土台の中に入ったつもりで作業できます。\
カーネルは電話のものを共用するので、仮想マシンよりずっと軽く動きます。\
土台は3つから選べます。\
Ubuntu 24.04 と Alpine 3.24 と、Bionicのみ（土台なし）です。\
土台ごとに標準ライブラリが違います。\
Ubuntu は glibc、Alpine は musl、Bionicのみ は Android の Bionic です。\
公式の実行ファイルは glibc 前提の物が多いので、そういうソフトは Ubuntu の土台で動かします。

![土台の切り替え画面。Ubuntu 24.04 と Alpine 3.24 と Bionic が並んでいる](tech/hako-at-linux-base-switch-v1.jpg)

### 3 レシピで足すサービス

サービスは、箱の中から `hako up 名前` で足します。\
レシピは数KBの設定ファイルで、入手先と入れ方だけが書いてあります。\
本体は、入れる時に公式の配布元から取ってきて、ハッシュで照合します。\
カタログは [Hako Hub](https://oosawak.github.io/materials/hako-hub/) に置いてあります（テスト公開中）。\
nginx と code-server と Forgejo は、実機で入れて動くところまで確認済みです。

## proot の性格と付き合い方

proot の変換には、代償があります。\
git の操作を、土台の中と外で比べると、中の方が遅い結果になりました。\
切り分けると、原因は proot の ptrace の変換でした。\
外で動くネイティブの git（clone の中央値 510 ミリ秒）に対して、中は 1,143 ミリ秒でした。\
この実測から、置き方の振り分けが決まりました。\
速さが要る物はネイティブ側に、互換性が要る物は土台の中に置きます。\
もう1つ、土台の中では、パッケージをまとめて新しくする操作（`apt upgrade`）を止める仕組みを入れています。\
変換層と新しいライブラリの組み合わせが合わないと、箱が動かなくなるためです。\
個別に足す操作は自由で、土台を上げる時は土台ファイルごと差し替えます。\
Alpine を proot で動かす実測もしています。\
土台ファイル 3.84 MiB の展開は 0.51 秒で、git と nginx と Python を入れても合計 69.5 MiB でした。\
git の操作も、Ubuntu の土台より約22%速い結果でした。

## 入り口は Rust の sshd

以前の構成では、SSH サーバーは土台の中の OpenSSH でした。\
入り口が土台に依存するのは弱点なので、ネイティブ化しました。\
候補は、Dropbear と、Rust のライブラリ russh です。\
両方を作って、同じ電話（Pixel 4）で比べました。\
起動は russh が 26.63 ミリ秒、Dropbear が 33.62 ミリ秒でした。\
待ち受けのメモリは、russh が 2,536 KiB、Dropbear が 2,868 KiB でした。\
大きさだけは Dropbear の勝ちで、297 KB に対して russh は 1.66 MB です。\
決め手は、SFTP のサーバーが russh 側で揃うことと、パスワードの照合を自前で持てることでした。\
採用は russh です。\
Rust のライブラリ russh を使って、SSH サーバーを自作したものです。\
本実装の実測では、起動 14.0 ミリ秒、待ち受けのメモリ 2.43 MiB、本体の大きさ 1.70 MiB でした。\
土台が動いている時は、その土台のシェルにつなぎます。\
土台が止まっている時は、Bionic 側のシェルで応答します。\
入り口が生きているので、土台の調子が悪い時の復旧口にもなります。

## 初回セットアップと認証

初回セットアップでは、土台と、初期ユーザー（既定は hako）と、パスワードを設定します。\
root のパスワードも、ここで決めます。\
照合は Argon2id のハッシュで行い、パスワードが未設定の間は SSH を開きません。

## センサーブリッジ

電話には、測る部品が最初から入っています。\
これを箱の中から使えるように、ローカル専用（127.0.0.1）の橋を作りました。\
橋は HTTP の JSON で、追加のアプリは要りません。\
`hako-sensor` というコマンドと、Python のライブラリ（`hako_sensor.py`）を用意しました。\
取れるのは、気圧と照度と加速度とジャイロと地磁気と近接と、バッテリーの状態です。\
Pixel 4 の実測では、気圧 995.2 hPa、照度 219.35 lux、バッテリー 79%（27.1℃）が取れました。\
Pixel 3a と Pixel 7a でも、同じ形で取れることを確認しています。\
アプリの画面にも、センサーの現在値が出るようになりました。\

![センサーの現在値がアプリの画面に出ている様子。気圧と照度と電池と加速度](tech/hako-at-linux-sensor-v1.png)
測る、記録する、送る、が1台で完結するのが、Hako@Linux の面白さです。

### 参考：Doze の中でも記録が続くかと電源消費について

画面を消して充電もしない状態で、センサーの記録がどこまで続くかを試しました。\
条件は、60秒間隔で記録して、1時間置くことです。\
Pixel 4（Snapdragon 855、Android 13）では、62.2 分で 63 回の記録が取れて、欠けはゼロでした。\
電池は 82% から 73% で、1時間で 9% の消費でした。\
Pixel 3a（Snapdragon 670、Android 15）では、61.7 分で 62 回の記録が取れて、こちらも欠けはゼロでした。\
電池は 96% から 94% で、1時間で 2% の消費でした。\
計算では、満充電で約 50 時間の記録が続けられます。\
温度と気圧と照度も、両方の機種で記録できていました。\
置きっぱなしの環境センサーとして使うには、十分すぎる結果です。\
これは実験段階での測定です。\
センサーを足したり、記録の間隔を変えたりすれば、消費の数字は変わります。

## 実測のまとめ

Hako@Linux だけの状態（Pixel 3a）では、起動が 879 ミリ秒、待機メモリが 37.9 MiB でした。\
土台のセットアップ（Pixel 4）は、Ubuntu 24.04 が 49.0 秒で 229.9 MiB、Alpine 3.24 が 6.7 秒で 25.9 MiB でした。\
サービスの実測では、Forgejo を常駐させると全体で約 222.6 MiB になり、その大半は Forgejo 自身（155.4 MiB）でした。\
重いのは土台ではなく、載せるサービスの方だということです。

## 16KB ページ対応（tips）

新しい Android の端末では、メモリのページの大きさが 16KB になっています。\
ネイティブの部品は、作る時に配置を 16KB に揃えないと、そういう端末では動きません。\
揃え方は、リンクの時に `-Wl,-z,max-page-size=16384` を付けることです。\
部品がたくさんあると、1つでも漏れると、その部品だけが落ちます。\
箱では、全部品にこの対応を入れるのを決め事にしています。\
箱の部品では実際に対応を入れてあり、全部品（実行ファイル14個）で揃っていることと、16KB ページの端末（Pixel 7a）でも動くことを確認しています。
