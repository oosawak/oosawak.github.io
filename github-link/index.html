1

GitHub ってなに？

ひとことで言うと「履歴のついた、インターネット上のファイル置き場」

GitHub（ギットハブ）は、インターネット上にあるファイル置き場のサービスです。 ふつうのファイル置き場と違うのは、「いつ・誰が・何を変えたか」が全部、履歴として残ることです。 間違えて消したり壊したりしても、履歴をたどれば前の状態に戻れます。

もともとはプログラマーがプログラムを置く場所として広まりました。 ただ、中身はただのファイル置き場なので、文章、メモ、資料、写真のようなファイルでも置けます。 「エンジニアの道具だから自分には関係ない」という身構えは、ここで外して大丈夫です。

この資料で大事な、3つの言葉だけ先に

リポジトリ（置き場）
GitHub の中に作る、プロジェクトごとの保管庫です。フォルダを丸ごと預けるイメージで大丈夫です。英語では repository と書きます。
コミット（履歴に記録）
その時点の状態を「ここまでの記録」として残すことです。ゲームのセーブデータのように、あとからその時点へ戻れます。
プッシュ／プル
プッシュは「自分の側のファイルを置き場へ送る」、プルは「置き場の新しいファイルを自分の側へ受け取る」という意味です。送る・受け取る、と読めば十分です。
Git（ギット）
履歴を記録する仕組みそのものの名前です。GitHub は、その仕組みを使った置き場を貸してくれるサービス、という関係です。
安心材料を先に： 操作の多くは、ミューズや Codex のような AI に「やって」と頼めます。 置き場の用意の仕方だけ分かれば、細かい操作は AI と分担できます。 この資料の目的も、「全部を自分で覚える」ことではなく「全体の形が分かる」ことです。

なぜ GitHub か

無料で、人と AI が同じファイルを見られて、履歴が残るから

AI 同士に連携して働いてもらうには、「2人ともが見られる場所」にファイルを置く必要があります。 その場所の候補はいくつかありますが（第3章）、まず GitHub を勧める理由は次の通りです。

無料の範囲で、十分に使えます

GitHub はアカウントを作るのも、ファイルの置き場を作るのも無料で始められます。 非公開の置き場（第4章で説明します）も無料で作れます。 AI 同士の受け渡しのような使い方なら、ふつうは無料の範囲に収まります。

人・ミューズ・Codex が、同じファイルを見られます

置き場がインターネット上にあるので、あなた自身も、ミューズも、Codex も、 同じファイルを読み書きできます。 「ミューズが書いた指示書を、Codex が読んで実行する」といった受け渡しは、この形だから成り立ちます。 メールの添付ファイルを送り合う形と違って、常に「最新の1つ」がそこにある、というのも利点です。

履歴が全部残ります

  • いつ、誰（どの AI）が、何を変えたかが記録されます
  • 「昨日の状態に戻したい」が、履歴をたどってできます
  • 指示書や報告も履歴ごと残るので、あとから経緯を確かめられます

色々なものを残せます

プログラムだけの場所ではありません。指示書、報告、仕様書、設計メモ、メモリーの写し、作った資料の一覧まで、 仕事の材料をまとめて置けます。詳しい例は第9章にまとめました。

置き場だけではありません

置く

置き場所

ファイルと履歴を預ける保管庫。受け渡しの土台です（第4章・第5章）。

配る

配る場所

置いた HTML を、そのまま Web サイトとして公開できます。GitHub Pages の話です（第6章）。

回す

自動で回す場所

更新をきっかけに、決まった作業を自動で走らせられます。GitHub Actions の話です（第7章）。

「置く・配る・回す」が1か所で済むのが、GitHub を土台にする一番の理由です。

3

他のやり方もある

専用ツールや共有フォルダという道も。まずは無料の GitHub で十分です

AI の受け渡しの場所は、GitHub 以外にもあります。 どういうものがあるか、事実として紹介しておきます。

Obsidian のようなメモアプリの共有フォルダ

Obsidian（オブシディアン）は、手元のフォルダに文章（Markdown）をためるメモアプリです。 そのフォルダを共有すれば、AI との受け渡しの場所にも使えます。 「自分のメモ帳と地続き」という手軽さがあります。 一方で、他のパソコンや AI から見られるようにするには、共有の仕組みを別に用意する必要があることが多いです。

専用の連携ツール

AI 同士をつなぐための専用ツールやサービスもあります。 連携に特化している分、便利な機能が付いていることもあります。 ただ、道具が増えると、覚えることと管理する場所も増えます。

この資料の位置づけ

まず無料の GitHub で十分、がこの資料の立場です。 置き場・履歴・受け渡し・公開・自動実行までが無料の範囲でそろうので、 まずは GitHub だけで始めるのが無理のない順番です。

書いている人の立場

最後に、書いている人の立場をはっきり書いておきます。 正直なところ、私は GitHub 以外を使うのはナンセンスだと思っています。 私がやりたいことは、大体 GitHub でできるからです。 置き場も、受け渡しも、公開も、自動で回すのも、ここ1つで済んでいます。 他のやり方の紹介はしましたが、私は使うつもりはありません。 道具と置き場所は増やさない。それが私のやり方です。

4

つなぎ方の手順

アカウント作り → 非公開の置き場 → フォルダ分け → AI たちにつなぐ → 巡回

ここからは実際の手順です。画面は英語が多いので、出てくる言葉はその都度かみ砕きます。 画面の細部は時期によって少し変わりますが、大まかな流れは同じです。

手順1：アカウントを作る

1

GitHub のサイトを開いて「Sign up」を押す

ブラウザで github.com を開きます。右上にある Sign up は「登録する」という意味です。

2

メールアドレス・パスワード・アカウント名を入れる

Email はメールアドレス、Password はパスワード（合い言葉）、Username はアカウント名です。アカウント名は、あとで出てくる公開ページの住所にも使われる名前なので、人に見せても困らないものにします。

3

本人確認をして「Create account」を押す

登録の途中で、「人間かどうか」の確認（絵や文字を選ぶ小さなテスト）や、メールに届く数字の入力を求められます。Create account は「アカウントを作る」という意味です。これで登録は完了です。

パスワードは他と使い回さないでください。 あわせて、ログイン時にスマホ等でもう一段階確認する「2要素認証」を入れておくと、アカウントを守れます。 設定の場所が分からなければ、ここも AI に聞きながら進めて大丈夫です。

手順2：非公開の置き場（リポジトリ）を作る

1

「New repository」を押す

ログインした画面で、緑色の New（新しい）ボタン、または New repository を選びます。repository が第1章の「置き場（リポジトリ）」のことです。

2

名前を付けて、Private を選ぶ

Repository name が置き場の名前です（例： ai-work）。公開範囲は2択で、Public は「誰でも見られる」、Private は「自分と、招待した人だけ」です。AI との受け渡し用には Private を選びます。

3

「Create repository」で完成

Create repository（置き場を作る）を押せば、空の置き場ができます。最初は空っぽで正常です。

Public と Private の線引き： 迷ったら Private です。人に見せるためのものだけ、別の Public の置き場に分けて置くのが安全です（第6章の公開の話にもつながります）。

手順3：フォルダの分け方を決める

置き場の中は、用途ごとにフォルダを分けておくと、AI 同士の受け渡しが迷子になりません。 分け方に決まりはありませんが、たとえばこういう形が使いやすいです。 

（置き場の中身の例）

tasks/    … 指示書を置く場所（AI への仕事の明細）
reports/  … 報告が戻ってくる場所（実行した結果）
docs/     … 仕様書や資料の場所
memory/   … メモリーの写しを置く場所

フォルダ名は英語の小文字にしておくと、どの道具からでも扱いやすくなります。 置き場の中にファイルやフォルダを作る作業も、ブラウザの画面からできますし、AI に頼んでも大丈夫です。

手順4：ミューズと Codex につなぐ

置き場ができたら、次は「それぞれが、その置き場を読み書きできる」状態にします。 イメージは、同じ保管庫の合鍵を、それぞれに1本ずつ渡す感じです。

  • ミューズ側： 置き場のファイルを読み、指示書を書いて置けるようにします。多くの場合、ミューズに「このリポジトリで作業して」と頼むところから始まります。
  • Codex 側： Codex が動くパソコンに置き場の写しを用意し、受け取って実行し、結果を送り返せるようにします。パソコン側の受け渡しには Git という道具が働きます。
  • 人（あなた）： ブラウザで置き場を開けば、いつでも中身と履歴を見られます。作業の「確認」はこの画面でできます。
接続の設定は、AI に頼んでいい部分です。 「このリポジトリにつないで」「置き場の写しを用意して」と頼めば、具体的な操作は AI が進めてくれます。 あなたが覚えるのは、「誰が・どの置き場を・読み書きするか」の線引きだけです。

手順5：「巡回」という考え方を知る

置き場に指示書を置いても、相手が気づかなければ仕事は始まりません。 そこで使われるのが 巡回（じゅんかい）です。 「決まった間隔で置き場を見に行き、新しい指示書があれば拾って実行する」という約束を、受け取る側の AI に持たせます。

人間同士で言えば、「置いておくから、ときどき見といてね」と同じです。 ずっと張り付くのではなく、間隔を決めて見に行くので、無駄も少なく済みます。 巡回の間隔や、拾ったら印を付ける等の約束ごとは、第5章の「往復の流れ」の中で効いてきます。

5

往復の流れ

指示書を置く → 読んで実行 → 報告が戻る → 人が確認する

つながったあとの、日常の回り方はこの往復です。会話と判断はミューズ、実行は Codex、確認は人、という分担が基本形です。

1

人が頼む

「これを作って」「これを直して」と、まずミューズに相談します。相談の中で、仕事の中身が決まっていきます。

2

ミューズが指示書を書いて置く

決まった仕事を、指示書（Markdown のファイル）にして、置き場の tasks/ フォルダに置きます。指示書には、目的・やること・材料の場所・報告の形を書きます。

3

Codex が読んで実行する

巡回で指示書を見つけた Codex が、その仕事を実行します。着手したら、指示書に「実行中」の印を付けて戻す約束にしておくと、取り合いになりません。

4

報告が戻ってくる

終わったら、結果を報告ファイルにして reports/ に置き、指示書にも「完了」と状態を書き添えます。何をして、何ができて、何が残っているかが報告の中身です。

5

人が確認する

報告を読んで、出来上がりを確かめます。違うところがあれば、またミューズに相談して直してもらいます。この「確認してから次へ」が、安全に回すコツです。

指示書の見本

指示書は、ふつうの文章ファイル（Markdown）です。形はこれくらいシンプルで十分です。

# 指示書：自己紹介ページを作る

## 目的
（何のための仕事か。例：お店の紹介ページを新しく作る）

## やること
- （具体的な作業を箇条書きで書く）
- （できあがりのイメージもここに）

## 材料
- （使う文章や写真の置き場所を書く）

## 報告
- 終わったら reports/ に報告を書いてください
- できなかったことがあれば、その理由も書いてください

うまく回るコツ

  • 1つの指示書に、1つの仕事。 詰め込むと、どこまで終わったか分かりにくくなります。
  • ファイル名に日付と短い名前を。 たとえば 2026-11-08-intro-page.md のようにすると、並びも探しやすさも良くなります。
  • 報告の形まで指定する。 報告が同じ形で戻ってくると、確認がぐっと楽になります。
  • 指示書を書くのも、ミューズに頼めます。 相談の内容をそのまま指示書に整えてもらうのが、この分担の基本形です。

GitHub Pages：配る場所

置いた HTML が、そのまま Web サイトになる仕組み

GitHub Pages（ページズ）は、置き場に置いた HTML ファイルを、そのまま Web サイトとして公開できる仕組みです。 資料や小さなサイトの「配る場所」として使えます。自分でサーバーを用意する必要はありません。

公開のされ方

  • 公開すると、https://＜アカウント名＞.github.io/＜置き場の名前＞/ のような住所（URL）で、誰でも開けるページになります。
  • ファイルを置いてから画面に反映されるまで、少し時間がかかります（数分ほど待つつもりで）。置いた直後に開いて古いまま見えても、故障ではありません。
  • 無料の範囲で使えます。

配信の仕方は2通り

そのまま方式

置いたファイルを直接出す

置き場の HTML を、そのまま公開します。作りが単純なページはこちらで十分です。

Actions 方式

組み立ててから出す

第7章の Actions に「サイトを組み立てる」作業をさせて、その結果を公開します。材料（Markdown 等）から自動でページを作る場合はこちらです。

共通

どちらでも「置けば公開」

入門の段階では、方式の違いを細かく覚える必要はありません。「置いたら、少し待つと表に出る」が共通の感覚です。

大事な注意：Pages で出したページは、基本的に誰でも見られます。 無料で Pages を使えるのは公開（Public）の置き場です。 だから、「内部の受け渡し用の置き場（Private）」と「人に見せる用の置き場（Public）」は分けるのが基本形です。 見せたくないものを、公開側に混ぜないでください。

GitHub Actions：自動で回す場所

「更新されたら、この作業をして」を自動で実行する仕組み

GitHub Actions（アクションズ）は、決まった作業を自動で回す係です。 「ファイルが更新されたら、この作業をして」「毎朝この時刻に、このチェックをして」という決まりを置いておくと、 GitHub の側が自動で実行してくれます。自分のパソコンを付けっぱなしにする必要はありません。

きっかけ（トリガー）は2種類

  • 更新をきっかけに： ファイルが置き場に送られた（プッシュされた）ときに走ります。
  • 時刻をきっかけに： 決まった時刻の定期実行もできます（例：毎朝の定期処理）。

一般的な使い方の例

  • Markdown が更新されたら、自動でサイトを組み立てて公開する（第6章の「Actions 方式」がこれです）
  • 置いたファイルを、別の形に変換する（例：文章ファイルから、配布用のファイルを作る）
  • 毎朝、決まったチェックや集計を自動で回して、結果をファイルに残す

決まりは「手順書ファイル」に書きます

自動作業の決まりは、ワークフローという名前の手順書ファイルに書いて、置き場の .github/workflows/ というフォルダに置きます。書式は YAML（ヤムル）という形式です。 イメージはこのくらいです。 

# 手順書ファイルのイメージ（実際に使うときは AI に書いてもらえます）

name: サイトを組み立てる        # この自動作業の名前
on:
  push:                        # ファイルが更新されたら走る
  schedule:                    # 決まった時刻にも走る（定期実行）
    - cron: "0 21 * * *"       # 毎朝6時ごろ（日本時間）

※ 時刻の書き方は世界標準時が基準で、日本時間とは9時間ずれるため、上の例では 21時＝翌朝6時、と書いています。 こういう細かい決まりも含め、手順書ファイル自体は AI に書いてもらうのが現実的です。

まとめると： GitHub は「置き場所」であると同時に、Pages で「配る場所」になり、Actions で「自動で回す場所」にもなります。 だから受け渡しの土台にすると、仕事の材料から公開・自動処理までが、1か所でつながります。

守ること

秘密は書かない、公開範囲を分ける、実行は人の承認から

便利な仕組みほど、最初に線引きを決めておくことが大事です。守ることは、大きく3つだけです。

1. 秘密は、ファイルに書かない

パスワード、トークン（合鍵のような文字列）、鍵ファイルの中身は、指示書や資料に書いてはいけません。 GitHub は履歴が全部残る場所なので、一度書いたものは「履歴に残り続ける」前提で考えてください。 うっかり書いてしまったら、消して済ませようとせず、すぐに詳しい人に相談を。

2. 公開の置き場に、個人の情報を置かない

  • 受け渡しや内部の資料は Private（非公開）の置き場へ
  • 人に見せるものだけを、別の Public（公開）の置き場へ分ける
  • 住所・連絡先・内部のマシン名など、個人に紐づく具体的な値は、公開側では一般的な言い方に置き換える

3. 実行の根拠は、人の承認

AI 同士の往復は便利ですが、「誰も見ていないところで勝手に回り続ける」形にはしないのが原則です。 仕事の実行は人の承認や依頼を根拠にして、公開・送信・お金が絡むことは、必ず人が確認してから進めます。 報告を読んで人が確かめる、第5章の往復の最後の段が、そのための仕組みです。

合い言葉ひとつで言えば： 「秘密は書かない」「出す場所としまう場所を分ける」「要所は人が見る」。この3つを守れば、入門の範囲ではまず安全に回せます。

9

残せるものの例

プログラム以外にも、仕事の材料をまとめて残せます

置き場は「AI への通り道」であると同時に、「仕事の記録の棚」でもあります。 たとえば、こういうものが残せます。

指示書
AI への仕事の明細（第5章）。何を頼んだかが、履歴と一緒に残ります。
報告
実行の結果。「何をして、何ができて、何が残ったか」があとから追えます。
仕様書・設計メモ
作るものの決め事。AI に読ませる材料であると同時に、人のための記録にもなります。
メモリーの写し
ミューズが覚えていることの控えを置けます。本体の記録が薄れても、写しから経緯を確かめられます。
作ったものの一覧
作った資料・公開したページ・作った画像などの目録。あとから探す手間が減ります。
資料そのもの
この資料のような HTML や文章のファイル。Pages で配る元にもなります。

用語辞典

出てきた言葉を、短く平たい言葉で
GitHub（ギットハブ）
履歴のついた、インターネット上のファイル置き場サービス。この資料の主役です（第1章）。
Git（ギット）
ファイルの変更履歴を記録する仕組み。GitHub はこの仕組みを使ったサービスです。
リポジトリ（置き場）
GitHub の中に作る、プロジェクトごとの保管庫。英語では repository と書きます。
Public／Private
置き場の公開範囲。Public は誰でも見られる、Private は自分と招待した人だけです（第4章）。
コミット
その時点の状態を履歴として記録すること。あとから、その時点の状態に戻れます。
プッシュ／プル
プッシュは置き場へ送ること、プルは置き場から受け取ることです。
Markdown（マークダウン）
見出しや箇条書きを簡単な記号で書ける、文章ファイルの書式。指示書や仕様書によく使います。
指示書
AI への仕事の明細を書いたファイル。置き場経由で渡します（第5章）。
巡回
受け取る側の AI が、決まった間隔で置き場を見に行き、新しい指示書を拾う約束ごとです（第4章）。
GitHub Pages
置き場の HTML を、そのまま Web サイトとして公開できる仕組み（第6章）。
GitHub Actions
更新や時刻をきっかけに、決まった作業を自動で実行する仕組み（第7章）。
ワークフロー
Actions の自動作業の手順書ファイルのこと。.github/workflows/ に置きます。
トークン（秘密の側）
パスワードの代わりに使う、合鍵のような長い文字列。ファイルには書きません（第8章）。
2要素認証
パスワードに加えて、もう一段階の確認でログインを守る仕組みです。
