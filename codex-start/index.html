CODEX STARTER GUIDE

Codex と一緒に、
フォルダの中で物を作る。

Codex は、パソコンのフォルダの中身を読んで、書いて、直してくれる AI の相棒です。 このガイドは、ターミナル（黒い画面）に慣れていない人に向けて、 「最初の15分」の手順から、頼み方のコツ、言葉の意味までを順に案内します。

1

最初の15分

入れる → サインイン → フォルダで開く → 最初のひと言 → 出来上がりを見る

Codex の仕事場は「フォルダ」です。作りたい物が入るフォルダを決めて、その中で Codex を開くと、 Codex はそのフォルダの中身を見ながら作業します。まずは小さなフォルダで試すのがおすすめです。

1

Codex を入れる

ターミナルを開いて、次のどちらかを実行します。Mac では Homebrew、他の環境では npm を使う方法が一般的です。

brew install --cask codex
npm install -g @openai/codex
2

サインインする

ターミナルで codex と入力して Enter。初回はサインインを求められるので、 案内に従って ChatGPT アカウントでサインインします（API キーで使う方法もあります）。

3

作業フォルダの中で開く

ターミナルで作業したいフォルダへ移動してから codex を実行します。 たとえば「memos」というフォルダで始めたいなら、次のようにします。

cd ~/memos
codex
4

最初の依頼を出す

画面の下の入力欄に、やってほしいことを普通の文章で書いて Enter を押します。 最初は小さな頼みごとが安心です。

このフォルダの中身を一覧にして、それぞれ何のファイルか短く説明してください。ファイルは変更しないでください。
5

結果を確かめる

Codex が何をしたかは、画面の表示と、実際にフォルダの中身を開いて確かめます。 ファイルを書き換えたときは /diff と入力すると、変更箇所だけを表示してくれます。

15分のゴール： 「フォルダを開いて、ひと言頼んで、結果を見る」が一通りできれば十分です。 凝った物作りは次の章からで大丈夫です。
✓ 読了
2

画面と操作の基本

対話画面の見方と、止める・戻す・頼み直すの作法

画面は「会話の記録」です

Codex の画面には、あなたの依頼、Codex の考えや作業の様子、実行したコマンドとその結果が、 上から下へ時系列で並びます。迷ったら、まず一番下（最新の状態）を見てください。 入力欄は画面の下にあり、文章を書いて Enter で送信します。

途中で止めたいとき

  • 作業の途中で止めたいときは Esc キーを押します。今の作業が中断され、指示を出し直せます。
  • Codex が作業中でも、追加の文章を入力して送ると「次の指示」として受け取られます。急ぎの軌道修正は、まず Esc で止めてから伝える方が確実です。
  • 画面を終えるときは /quit と入力するか、Ctrl+C を2回押します。

承認を求められたら

ファイルの書き換えやコマンドの実行の前に、Codex が「実行してよいですか？」と聞いてくることがあります。 これは失敗ではなく、安全のための確認です。内容を見て、問題なければ許可（Yes）を選びます。 どんなときに聞かれるかは、次の章の「モードと安全」で決まります。

覚えておくと便利なコマンド

入力欄に / と打つと、使えるコマンドの一覧が出ます。最初はこの3つで十分です。

/diff    … Codex が加えた変更箇所を表示する
/status  … いまのモデルや設定の状態を表示する
/model   … 使うモデルを切り替える

「戻す」はフォルダごと守る

作業フォルダを Git で管理しておくと、「さっきの状態に戻す」が簡単になります。 Git を使っていないフォルダでは、大事なファイルを先にコピーしておくのが安全です。 Codex 自身にも「変更を元に戻して」と頼めますが、確実なのは自分側の控えです。

注意： うまくいかなかったときに慌てて同じ指示を連打すると、変更が重なって余計に分からなくなります。 一度止めて、「何が起きたか説明して」と聞くのが近道です。

モードと安全の基本

「どこまで自由にやっていいか」を決める2つのスイッチ

Codex の動き方は、大きく2つの考え方で決まります。 ひとつは サンドボックス（触れる範囲）、もうひとつは 承認（実行前に聞くかどうか）です。 難しく考えず、「範囲」と「確認」の2つだと思ってください。

サンドボックス ＝ 触れる範囲

READ-ONLY

読むだけ

ファイルを読むことはできますが、書き換えはできません。相談や調査だけしたいときに。

WORKSPACE-WRITE

作業フォルダの中は自由

開いたフォルダの中は読み書きできますが、その外には手を出しません。ふだんの作業はこれが基本です。

FULL ACCESS

全部許可

パソコン全体に触れます。便利ですが、影響も大きくなります。何をしているか分かっているときだけ選びます。

承認 ＝ 実行前に聞くかどうか

  • こまめに聞く： 書き換えやコマンドのたびに確認が出ます。最初はこの状態で、Codex の動き方に慣れるのがおすすめです。
  • 範囲内は聞かない： 作業フォルダの中のことは自動で進み、範囲の外に出るときだけ聞かれます。慣れてきたらこの形が快適です。
  • ほとんど聞かない： 確認なしで進みます。作業は速くなりますが、見守る前提の使い方です。

画面では /approvals と入力すると、いまの承認のされ方を確認・変更できます。 組み合わせの目安はシンプルで、大事なフォルダほど「狭く・こまめに」、試作用のフォルダほど「広く・自動で」です。

ネットワークについて： 標準では、作業中のコマンドからインターネットへ出る通信は制限されています。 必要な場合だけ、設定で許可できます（第7章参照）。

良い依頼文のコツは3つです。①何をしてほしいか、②対象はどれか、③やってはいけないことを添えること。 下の見本はどれも、この3つが入る形にしてあります。

作る 6本

ブラウザで開けるページ

見た目のある成果物がほしいとき

文章づくりのたたき台がほしいとき

フォルダと土台を用意する

新しい作業を始めるとき
新しいプロジェクト用に、このフォルダの中に docs、src、data の3つのフォルダを作ってください。それぞれの用途を書いた README.md も置いてください。

データを集計したいとき

template.md をひな形にして、items.txt に書かれた名前ごとに1ファイルずつ、pages フォルダへ作ってください。名前の部分だけ差し替えて、他の文面は変えないでください。
直す 5本

エラーを見てもらう

動かなくなったときの第一声
このプログラムを実行するとエラーが出ます。エラーの文面を貼るので、原因を教えてください。いきなり直さず、まず原因の見立てを聞かせてください。

直し方を小さく区切る

大きな修正を安全に進めたいとき
今のエラーを直してください。ただし変更は最小限にして、直した場所と理由を1か所ずつ説明してください。関係ない場所は触らないでください。

見た目の崩れを直す

ページの表示がおかしいとき
index.html をスマホで見ると、右側に余白ができて横にずれます。原因を探して直してください。デザインそのものは変えないでください。

文章の表記をそろえる

文面の整え直し
docs フォルダの文章で、「ください」と「下さい」の表記が混ざっています。「ください」に統一してください。意味や言い回しは変えないでください。

元に戻してもらう

直し方が気にいらないとき
さっきの変更を元に戻してください。戻したあと、代わりにどうすればいいか、案を2つ出してください。勝手に別の変更はしないでください。

中身の地図を作る

初めてのフォルダを前にしたとき
このフォルダの全体像を教えてください。何を作るための場所で、主要なファイルはどれで、それぞれ何の役割ですか。変更はしないでください。

どこに書いてあるか知りたいとき

資料が増えてきたとき
docs フォルダの文章を通して読み、同じ内容の重複と、食い違っている記述を探してください。場所と内容を一覧にしてください。直すかどうかは私が決めるので、変更はしないでください。

片づけの前の現状把握

動かして確かめる

直したあとの確認
さっき直したプログラムを実際に動かして、エラーが出ないか確認してください。実行したコマンドと結果をそのまま見せてください。

確かめる手順を書く

自分で確かめたいとき
このページが正しく動くか、私が自分で確かめるための手順を書いてください。開く場所、押す場所、どうなれば正常かを、順番に短く書いてください。

テストを用意する

変更点を要約する

作業の締めに
今日の作業で変更した内容を、3行で要約してください。どのファイルに、何のために手を入れたかが分かるようにしてください。

さっきの説明に出てきた「リファクタリング」という言葉を、身近な例えで説明してください。1分で読める長さにしてください。

AGENTS.md の書き方

「この場所での約束」をファイルに残すと、毎回説明しなくて済みます

フォルダの中に AGENTS.md という名前の文章ファイルを置いておくと、 Codex は作業の前にそれを読み、そのフォルダでの約束として守ります。 たとえば「出力は output フォルダへ」「勝手に消さないで」のような決まりを、毎回チャットで言わなくて済むようになります。

作り方

画面で /init と入力すると、そのフォルダ用の AGENTS.md の土台を Codex が作ってくれます。 あとは自分の言葉で書き足したり、Codex に「約束を追記して」と頼んだりして育てます。

書くと効くこと

  • このフォルダは何の場所か（何を作っているか）
  • 触ってほしくない場所（元データ、公開済みのもの）
  • 出力の置き場所や名前の付け方
  • 作業の進め方（区切りごとに報告する、公開前に必ず確認を取る、など）
  • 文章の約束（表記の統一、敬語の有無など）

見本

# このフォルダの約束

- ここは地域のお店を紹介する原稿置き場です。
- 原稿は drafts/ に Markdown で置きます。
- 元データ（data/）は読み取りだけ。書き換えや削除はしません。
- 表記は「ください」に統一します。
- 公開用の書き出しをする前に、必ず私に確認してください。
置き場所の小ワザ： AGENTS.md は、フォルダの中のさらに下のフォルダにも置けます。その場合、下のフォルダでは近い方の約束が優先されます。 また、パソコン全体で効く約束は、ホームの ~/.codex/AGENTS.md に置きます。
AGENTS.md は「常駐の約束」： ここで扱ったのは、ずっと効き続ける約束です。一回ごとの仕事の明細は、別の Markdown ファイルに書いて渡します。 その書き方は次の第6章で扱います。

6

Markdown で仕事を渡す

AGENTS.md の約束とは別に、一回ごとの仕事もファイルで渡せます

第5章の AGENTS.md は「常駐の約束」でした。でも、Codex とのやり取りで使う Markdown は、それだけではありません。 一回ごとの仕事の明細、作るものの決め事、終わったあとの報告――それらも Markdown のファイルで受け渡すと、 仕事がぐっと回しやすくなります。

なぜ Markdown なのか

  • そのまま読めるテキスト： 特別なソフトがなくても開けて、人が読んで、その場で直せます。
  • AI が読み書きできる： Codex をはじめ、AI は Markdown の文章をそのまま扱えます。画面に貼る文章も、ファイルに書く文章も、同じ言葉で通じます。
  • ファイルとして残る： チャットの流れの中に消えてしまわず、「何を頼んで、何が返ってきたか」をあとから見返せます。
  • 版の管理ができる： GitHub などの仕組みに乗せると、いつ・何が変わったかという履歴が残ります。

AGENTS.md 以外の Markdown たち

  • 指示書： 一回ごとの仕事の明細を書いたファイルです。目的、材料、やること、報告の形まで書いて渡すと、口頭の頼みごとより漏れが減ります。
  • 仕様書・設計メモ： 作るものの決め事を書いて残し、Codex に読ませます。会話の中で決めただけだと流れてしまいますが、ファイルに残せば次回も同じ前提で始められます。
  • 報告： 実行した結果を、同じファイルの末尾や、報告用のフォルダのファイルに書き戻してもらいます。人はあとからまとめて確認できます。
  • テンプレート： 指示書の「型」をあらかじめ用意しておくと、毎回同じ形で頼めます。型があると、書く側も読む側も迷いません。

指示書テンプレートの見本

新しく作るフォルダに、この型を1枚置いておくのがおすすめです。仕事のたびにコピーして使います。

# 指示書：（仕事の名前）

## 目的
（何のための仕事か。終わったとき、どうなっていれば成功か）

## 材料・置き場所
- 対象のフォルダ／ファイル：（場所を書く）
- 参考にしてよい資料：（あれば書く）

## やること
1. （頼みたい作業を、順番に書く）
2.
3.

## やってはいけないこと
- （触ってほしくないもの。勝手に公開・送信しないことなど）

## 報告の形
- このファイルの末尾に「状態：完了／未完了」と、やったことの要約を書き戻してください。
- 進めるうちに分からない点が出たら、作業を止めて「要確認」と書いてください。

往復の流れ

1

指示書を書く

テンプレートに沿って、その回の仕事の明細をファイルに書きます。

2

Codex が読んで実行する

ファイルの置き場所を伝えると、Codex はそれを読んで作業します。

3

状態と報告が書き戻る

終わったら、同じファイルの末尾や報告ファイルに、結果が Markdown で残ります。

4

人が確認する

報告を読んで、よければ次の指示書へ。直してほしい点は、次の指示に書きます。

使い分け： その場で対話しながら詰める仕事は、チャットが向いています。 時間をおいて実行してほしい仕事や、記録を残したい仕事は、この章の「ファイルで渡す」形が向いています。 なお、常駐の約束である AGENTS.md の書き方は、第5章で扱いました。

設定の入口

config.toml の場所と、入門のうちに触る項目だけ

Codex の設定は、ホームフォルダの中の ~/.codex/config.toml というファイルに書かれています。 特定のフォルダだけの設定は、そのフォルダの .codex/config.toml に書けます。 入門の段階では、次の3つを知っていれば十分です。 

# ~/.codex/config.toml の例

# 使うモデル
model = "gpt-5-codex"

# 承認のされ方（第3章の考え方と対応します）
approval_policy = "on-request"

# 触れる範囲
sandbox_mode = "workspace-write"
  • model ― どのモデルに仕事を頼むか。
  • approval_policy ― 確認の頻度。on-request は「必要なときに聞く」という意味です。
  • sandbox_mode ― 触れる範囲。第3章の3段階（read-only / workspace-write / danger-full-access）と対応します。

一時的に変えたいだけなら、起動時に codex -c approval_policy='"on-request"' のように -c で上書きもできます。まずはファイル側を正として整えるのがおすすめです。

もっと深い設定や、困ったときの直し方は： 設定でつまずいたときの切り分け手順は、姉妹編の「Codex CLI 設定・攻略ガイド」にまとめてあります。

8

ミューズと連動して使う

会話と判断はミューズ、実行は Codex。受け渡しは Markdown ファイルで

Codex は、フォルダの中で実行する役として頼りになります。一方で、相談したり、方針を決めたり、 進み具合を確認したりするのは、チャット型の相棒の方が向いている場面もあります。 そこで、別の AI エージェント「ミューズ（Muse）」と Codex を組み合わせる形を紹介します。 ここで紹介するのは、実際に家庭の環境で回している運用を、固有名や細部を外して一般化したものです。

考え方：直接つながず、ファイルで受け渡す

役割分担はシンプルです。会話と判断はミューズ（スマホから話しかけて、相談・方針決め・結果の確認をする）、 実行は Codex（パソコンやサーバーの中で、ファイルの読み書きやコマンドの実行をする）。 大事なのは、この2つを直接つながないことです。受け渡しは、GitHub 上に置いた Markdown ファイル―― 第6章の「指示書」と「報告」――だけで行います。いわば、決めた場所に置き手紙をする方式です。

往復の流れ

1

ミューズが指示書を書く

人との相談をもとに、目的・やること・報告の形を Markdown の指示書にまとめます（第6章の型がそのまま使えます）。

2

決めたフォルダに置く

指示書は、GitHub 上の「指示書置き場」に置きます。置き場所は最初に1つ決めておきます。

3

Codex が見に来て実行する

Codex は定期的に置き場を確認し、新しい指示書があれば、そのうち自分が担当するものを実行します。

4

報告を書いて戻す

結果は報告ファイルに書き、指示書の側にも「完了」などの状態を書き添えます。

5

人が報告を確認する

報告を読んで、次の判断をします。途中経過もファイルに残るので、あとから追いかけられます。

なぜ GitHub 経由なのか

  • 一か所で済む： 置き場所、履歴、受け渡しが GitHub の上に集まります。誰が・いつ・何を渡して、何が返ってきたかが残ります。
  • 常時接続がいらない： 2つの AI を直接つなぐ特別な仕組みがなくても、ファイルが届けば回ります。片方が止まっている間も、ファイルは置き場に残ります。
安全の線引き： 実行の根拠は、いつも人の承認です。指示書が置かれていること自体は、「やっていい」という許可ではありません。 とくに、公開・送信・お金が絡むことは、実行の前に必ず人が確認します。 分からない点が出たら進めずに「要確認」と書いて止まる――その約束も、指示書の型に入れておきます。
この章の続きは別資料で： GitHub へのつなぎ方の詳しい手順は、別資料『GitHub でつなぐ』にまとめます。 また、ミューズ側から見た使い方（何を相談し、報告をどう読むか）は「ミューズ使い方ガイド」にまとめてあります。

用語辞典

出てきた言葉を、短く平たい言葉で
ターミナル（黒い画面）
文字で命令を打つための画面。macOS では「ターミナル」、Windows では「ターミナル」や「PowerShell」がこれにあたります。
フォルダ／ディレクトリ
ファイルを入れる箱。ディレクトリはフォルダの技術寄りの呼び方で、意味は同じです。
リポジトリ
Git で管理されているフォルダ全体のこと。「この作業の保管庫」くらいの意味です。
コミット
その時点の状態を、履歴として記録すること。あとから「あのときの状態」に戻れます。
差分（diff）
変更の前後で、どこがどう変わったかの一覧。Codex の変更確認は /diff で見ます。
サンドボックス
Codex が触れる範囲を制限する仕組み。「砂場の中だけで遊ぶ」というイメージです（第3章）。
承認（approval）
書き換えやコマンド実行の前に、Codex があなたに許可を求めること。
モデル
実際に考えて作業する AI の種類。速さと賢さのバランスが違います。/model で切り替えます。
トークン
AI が文章を読み書きするときの、文字の数え方の単位。使用量の目安になります。
依頼文（プロンプト）
Codex への頼みごとの文章。このガイドの第4章の見本がそれです。
AGENTS.md
フォルダごとの約束を書いておくファイル。Codex が作業前に読みます（第5章）。
Markdown（マークダウン）
# や - などの記号で見出しや箇条書きを表す、テキストファイルの書き方。そのまま読めるので、人と AI の受け渡しに向きます（第6章）。
指示書
一回ごとの仕事の明細を書いた Markdown ファイル。目的・材料・やること・報告の形を書いて渡します（第6章）。
config.toml
Codex の設定ファイル。モデルや承認のされ方などを書きます（第7章）。
スラッシュコマンド
入力欄で / から始める命令。/diff や /status のように、会話とは別に直接指示します。
テスト
プログラムが期待どおり動くかを確かめる仕組みや作業のこと。壊れた箇所を早く見つけられます。
ミューズ（Muse）
チャットで相談や判断ができる AI エージェント。第8章では、Codex と役割分担する相棒として登場します。
